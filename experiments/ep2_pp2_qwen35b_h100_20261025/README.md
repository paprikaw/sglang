# 单张 H100 能容纳的模型：双卡 EP2 与 PP2

模型使用已校验的 Qwen3.6-35B-A3B BF16，完整检查点约 67 GiB；本轮只加载完整语言模型、
不启用视觉编码器，加载后 GPU allocated 约 64.7 GiB。语言模型 40 层、
每层 256 个路由专家、每 token 激活 8 个专家。全 Attention 与线性 Attention
按一比三混合，最大原生序列长度 262144 token。正式双卡对照前，先在同一租约内用
GPU0 加载全部 40 层并执行真实 4096 输入／4 输出请求，记录非零 KV 容量，再清理该进程。

两种配置都用两张 H100 80GB。EP2：Attention 每卡独立处理一半请求，专家跨两卡分配；
PP2：每阶段 20 层，每层全部专家；Decode 将整批请求平均分为两个槽位。
Prefill 另受每个 Attention 实例 4096 个新增 token 的实际 chunk 预算约束，
可能拆成更多 forward，不能把请求数上限解释成每个 Prefill forward 的实际 batch。
同节点两对 NVLink GPU 并行测试，复用已有完整 CPU 权重 Bank；没有新申请 GPU。
不使用合成 KV、CPU KV 换入、MTP 或跨请求共享前缀。

先加载两种配置，实测包括通信缓冲、Graph 和线性状态池在内的 KV 容量。
EP 容量汇总两个独立 Attention 实例；PP 的两份分层 KV 池只代表同一组请求，不能相加。

| 负载 | 请求数 | 每条旧 context | Prefill | Decode |
|---|---:|---|---|---|
| 中等 | 8 | Prefill 不缓存；Decode 已在 GPU 缓存 4096 token | 每条新输入 4096，输出 1 | 新输入 1，输出 128 |
| 长缓存 | 16 | 两种配置共同 KV 容量约 90%，平均分配并按 64 token 对齐 | 每条新输入 512，输出 1 | 新输入 1，输出 128 |
| 长缓存、较大 batch | 32 | 总旧 context 同上，平均分配到更多请求 | 每条新输入 512，输出 1 | 新输入 1，输出 128 |

若 PP 自身 KV 容量明显更大，补一个 PP 自身约 90% 的边界点，并标为非同工作量对照。
每个正式点先做相同形状预热，再采 3 次；旧 context 构建、预热与 profiler 都不计入正式时间。
吞吐仅计算本轮新输入或输出 token，记录 TTFT、TPOT、端到端延迟的均值、中位数和 P99。
另外分别采完整 Prefill cohort 和实际 Decode Graph 的短 trace，分开分析 Attention、
Routed/Shared Expert、Dispatch、Combine 与 PP 边界通信；不把内核累计耗时当成独占时间占比。

这是当前可用完整配置的比较：EP 支持原生 overlap，PP 沿用引擎支持的 PP 调度路径。
三轮只是描述性结果，不能证明稳定尾延迟或全局最佳 batch。

服务就绪后，三次启动均显式调用原生 `/freeze_gc`，排除跳过默认预热时自动 GC 回调
可能早于 HTTP socket 监听的竞争。该初始化不计正式时间；首次诊断运行 r1 保留但不参与最终对比。
r2 的单卡启动在读取该管理端点的纯文本应答时按 JSON 解析失败；已修正并加入 CPU 回归测试。
最终测量与资格数据只采用完成全部核验的运行。

最终 r3 原始 Guard 收尾因单卡 TP1 加载日志不带 TP0 标签而失败；实验本身完成，
EP／PP 多卡日志与清理有效。保存原始失败记录，并另做独立只读复核，检查冻结源码与布局、
日志原始 inode／新增字节哈希、原生资格和唯一 canonical 加载记录，不改 Guard 判定或策略。
