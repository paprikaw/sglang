# 35B：Decode 中是否需要动态调整 PP／EP 比例

本实验只验证必要条件：在相同单节点四卡预算下，优化 PP 是否在某些 workload 胜过全部已测的非 PP 候选，另一些 workload 是否有足够大的相反优势。没有测在线 autoscaling。

## 实验范围

- 两个已预约的四卡 H100 节点并行，但每个实例和四卡候选集合均不跨节点；不存在单节点八卡实测。
- 完整 Qwen3.6-35B-A3B，BF16 权重、BF16 KV、FP32 GDN。原模型 40 层、256 个 routed experts、top-8，未删减层或专家。
- 候选为 EP4、两个 EP2、两个优化 PP2、四个单卡副本、原生 PP4。Attention DP 与 EP 分别记录；EP4 的 Attention 为 DP4/TP1。
- 每请求通过真实 Prefill 建立 P256／4096／32768／131072 的 GPU 缓存。新增输入 Q1，贪心生成 128 个 token，忽略 EOS。
- 全节点并发 N8／16／32／64／128；长 context 只测 N8／32。输入包括固定模板和八主题文本。不是生产到达流量或质量 benchmark。
- 每格先单独预热，再保留全部三轮 profiler-off 正式样本；决定性结果另外确认。所有数字用算术平均；逐请求 TPOT、请求 E2E、TTFT 与整批完成时间分列。
- 逐请求检查原始 prompt 哈希、cached_tokens=P、输入 P+1、完整输出 128；不启用 HiCache 或 CPU KV 恢复。冷 Prefill 和启动不进入正式时间。

## PP2 的资格检查

两实例各有两个固定微批，每微批 N/4 个请求。所有请求的合批等待保留在客户延迟中。各点先记录原生固定分组的生成输出，再逐 token 检查优化 lookahead 输出完全相同。记录四个 stage 的 ahead／consumed／fast-send 计数与最终无未退休工作；正式时段另取四 rank 的 forward 与 Graph 资格计数。

新增加的 B32 静态消息形状保留原有 schema、GDN 边界和 ownership 检查。不能只凭“启用了 policy9”认定它实际生效，也不能把资格计数当成 GPU 活动分解。

## 显存配置

初版使用 native auto KV 和 0.95 静态比例，PP2 后续创建 NCCL channel 时无法再分配 10 MiB 缓冲区。该次失败不提供 PP2 性能数值。初版 EP 的 Mamba 池也把本地并发限制为 25，不能把 N128 的跳过归为 EP 的固有容量边界。

修订版保持相同 0.95 静态比例，给 KV 设置覆盖该内存档最大实际 workload 的上限，避免无用 KV 池占满显存，同时按原生 GDN slot 比率分配状态：

| 内存档 | N | P | 每完整模型 GPU 等价 GDN slots | 每完整模型 GPU 等价 KV token 上限 |
|---|---|---|---:|---:|
| short | 8／16／32／64 | 256／4096 | 80 | 73728 |
| dense | 128 | 256／4096 | 160 | 147456 |
| long | 8／32 | 32768／131072 | 48 | 1100032 |

PP 的 KV token 上限与 GDN slots 乘 PP stage 数，使每卡对应内存预算按层数换算；EP 的 GDN 参数乘 Attention DP 数，由原生引擎分到各 worker。每实例最大请求数按副本数分配。

实际 native KV 容量、GDN slots 和并发上限由启动日志与 API 读取。放不下的点另存 infeasible.json，不给 Decode 延迟。显存结论限于该数值类型、引擎和内存档；若结论依赖某个容量边界，需针对边界重新调参验证。

最终单卡 dense 档在0.95时未通过启动。补充仅针对 P256/N128，将比例调到0.98、KV上限设为32768（高于该点所需14336），可以启动，但未计时预热的 native GDN CoW 又需要1.82GiB临时内存并OOM。该尝试没有正式性能样本。没有把这个实现问题视为N128单卡的固有界限；P131072/N32的四单卡另有权重加KV的独立内存下界。

## 如何判断机制价值

1. 先画同节点所有已测候选的最佳性能包络，不能只比较 EP4 与 PP4，不能跨节点合并均值。
2. PP 如果被 EP4 或单卡副本覆盖，即使存在 EP4／PP2 的两两反转，也没有证明 PP 实例池的额外价值。
3. 在同一内存档内估算零切换成本的 cohort 选型：将两个 workload 的实测服务时间按混合权重加和，与最佳固定候选比较；再移除 PP 候选，看收益是否消失。
4. 这只是串行封闭 cohort 的时间代理，不能称为在线 goodput 或真实 autoscaling 收益，也不是任意调度器收益的普遍上界。
5. 双向至少约 20% 的最佳布局差异、至少约 10% 的理想选型收益，是预先记录的工程兴趣门槛，不是显著性检验。

权重常驻实例池会产生 batch 分流、队列、状态迁移及副本占卡成本。只有 PP 确实进入最佳包络，才值得进一步实现真实到达流的混合池；否则优先考虑 EP 规模与单卡副本之间更简单的选择。

原始运行不覆盖。每次启动由 Guard 验证已预约节点、CPU 权重命中、冻结源代码和拥有进程清理；失败尝试及原因在最终 RUN_AUDIT.md 单独记录。
