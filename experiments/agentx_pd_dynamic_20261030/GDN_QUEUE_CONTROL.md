# P/D 默认接收队列的容量控制

2026-10-31。准备并排队，尚无 GPU 结果；在所有前项通过后运行。

## 为什么必须补这项

此前 Decode 默认每 Attention-DP worker 的 32 个接收预留，将 GDN80 扩到 144，却没有在 KV 预算中扣除新增状态，导致启动 OOM。显式改为 8 个接收预留能避开该启动错误，但尚不知道较小队列是否限制 P/D 吞吐。不能仅用队列受限的结果判断 P/D 不值得做。

另一个待区分因素是 GDN 与 KV 的显存比例。现有 EP4/PP2 的实际前缀命中不同；总 GPU KV 较多不保证每个实例的状态缓存更适合当前轨迹。

因此在看到 E6 P/D 的正式结果前，增加一个有明确工程依据的容量配置控制，而不是搜索有利的负载或延迟目标。

## 固定对照

目录：`runs/eight_gpu_ep4_native_queue32_checkpoint_e6_r1`。

- 同 E6 commit `fc014e3553c4d234f38f3088a3158c0333e64830`，同8张H100、V3 AgentX派生请求、C128各三轮。
- 对比两节点的 **2×EP4合并** 与 **4P EP4→4D EP4**；双方每GPU完整模型等效 GDN 预算均为160。
- Decode接收预留保留默认32；活跃请求上限仍为每worker16。原生池需求上界 `(16+32)×3=144≤160`，KV预算在启动前按显式160槽位扣除状态显存。
- HiCache、每rank 32 decimal GB CPU预算、0.95静态显存比例和原生GPU KV自动容量保留；会话内不清缓存。
- 无额外GPU、无输入输出截短、无降低C128并发。真实GPU KV容量以ready/启动记录为准。

这是同版本、同预算下的两个容量调优候选。它同时改变状态池预算和接收预留，因此与80/8结果的差异不能全部归因于队列；这里要判断的是，更合理的固定P/D或合并配置是否改变结论。仍未修复所有引擎自动预算器路径。

预检已核对260项冻结哈希、原生命令、144≤160、串行参考和所有角色HiCache。后续必须通过实际池大小、输出一致性、全rank预热、全部六轮、Guard后检查及清理，才纳入已验收排名。
