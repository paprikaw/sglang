# EP4／PP4 缓存重放排名：逐轮复核

核查日期：2026-10-28。只分析已有文件，没有运行新 GPU 实验。固定 4×H100 NVLink、Qwen3.6-35B-A3B BF16、B64，每请求 P=130,304、Q=1、O=128。

此前将均值表直接当作部署排名反转的动机，证据表述偏强。逐轮结果仍有排名变化，但需要区分正常请求的性能、首 token 等待与一个显著延迟接入的请求。

| 协议／布局 | 三轮吞吐 tokens/s | 三轮中位数 |
|---|---|---:|
| GPU 自然命中 EP4 | 2326、2237、2312 | 2312 |
| GPU 自然命中 PP4 | 1696、1631、1647 | 1647 |
| CPU 受控重放 EP4 | 1584、1564、541 | 1564 |
| CPU 受控重放 PP4 | 1676、1663、1669 | 1669 |

原表的 1230 是 EP4 三轮吞吐的算术平均。第三轮 64 个请求中，63 个约 5.1 秒完成；一个请求等到 14.325 秒才收到首 token，15.143 秒完成。该轮批耗时为 15.148 秒，吞吐按 8192 / 批耗时计算，因而降到 541。平均吞吐对这一轮很敏感。CPU 模式下，原均值对应 PP4 领先约 35.8%，三轮中位数对应约 6.7%。保留全部有效样本；中位数只是敏感性分析，不构成删除慢轮或稳定优势的证明。

服务日志也支持“延迟进入执行”的定位：ep4.r0.log 的 6980–7039 附近，大部分请求于 11:21:16 开始响应，11:21:18 的 Decode rank 请求数为 15/16/16/16；11:21:30 才出现剩余请求的 HTTP 响应与 DP0 单请求 Prefill／Decode。批内客户端开始时间接近，无法用客户端有意晚发 14 秒解释。日志没有足够的逐请求接收、解析、路由与 admission 时间戳，不能进一步确认是 HTTP 传输、接入处理、tokenizer、缓存恢复等待或调度路径导致。

| 模式／布局 | 平均 TTFT 秒 | 平均 TPOT ms | 平均请求完成秒 |
|---|---:|---:|---:|
| GPU EP4 | 0.559 | 23.65 | 3.562 |
| GPU PP4 | 0.505 | 34.68 | 4.909 |
| CPU EP4 | 2.262 | 22.94 | 5.175 |
| CPU PP4 | 1.008 | 30.54 | 4.887 |

EP4 在两种模式下逐 token 生成都更快。CPU 模式 PP4 的优势体现于首 token 等待较短；不能据此说 PP4 的 Expert kernel 更快。平均请求耗时满足 TTFT + 127×TPOT，CPU 模式下 EP4 约多等 1.254 秒首 token、随后生成约节省 0.966 秒，两者抵消后平均请求完成时间只差约 0.288 秒。均值请求完成时间与整批吞吐衡量的对象不同。

PP4 两种模式都选择 policy=0/native、microbatch=16，故本例已经排除 PP 调优配置切换。GPU 模式 PP4 的 TTFT 比 CPU 模式少约 0.503 秒，但其后续 127 token 平均多用约 0.525 秒，二者抵消，使吞吐看起来几乎不变。两种模式使用不同新增 branch token 与缓存历史，生成轨迹和路由可能变化，无法由此推出“CPU 恢复无代价”。

当前可用结论：GPU 热缓存下 EP4 明显领先；CPU 重放下 PP4 的三轮典型批次表现略好，且本次没有 EP4 那样的长尾。现有证据尚不足以将其解释成缓存带宽导致的稳定架构优势。

若继续确认，优先固定相同输入、生成／路由工作量和 PP 设置，交替重复这四组点；同时补充客户端发送结束、HTTP 接收结束、tokenizer、各 rank loadback、入队与首轮执行时间戳。先解释那个延迟接入请求，再扩大扫描范围。
