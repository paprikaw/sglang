# AgentX workload 画像：数据集、当前回放、会话大小与缓存

2026-10-31，墨尔本。只分析已保存文件，未启动 GPU 实验。入口：[实验总索引](../README.md) · [逐请求／逐对话详细分布](../agentx_workload_profile_20261031/REPORT.md) · [实验与协议审计](../agentx_data_audit_20261031/REPORT.md)。

**AgentX 是编程代理的服务负载回放：多轮长前缀、工具等待、子代理并发，以及不断变化的 Prefill／Decode 压力。当前八卡实验选中的轨迹较短、输出较短，显式子代理覆盖也少；C128 主要放大了同一批轨迹的并发和缓存压力。**

## 1. 原始 workload 里有什么

官方数据来自自愿采集的 Claude Code 代理流量。保存的是输入／输出长度、时间、模型标签、会话／子代理关系及 64-token 前缀块哈希；不含原始代码、工具参数或工具结果正文。官方 harness 也以合成文本重建长度和前缀结构。测试目标是 serving 的吞吐、响应、缓存和调度，不提供编程任务成功率。

| 负载形态 | 测到的系统压力 | 数据中可以确认的范围 |
|---|---|---|
| 连续多轮主代理 | 长前缀重复访问、上下文增长、轮间停顿 | 393 个根会话；256k 版平均每族 173.7 次调用，中位数 70 |
| 显式子代理 | 多条请求链并行、父子依赖、分支生命周期 | 175/393 族有显式子代理；1,697 组、39,822 次内部调用 |
| 从扁平流重建的辅助分支 | 一次性 helper／sidecar、小链与父请求重叠 | 官方 loader 按时间、长度和模型关系识别；这是重建标签，不是可验证的语义任务类别 |
| 前台分支与后台分支 | 等待子任务返回的 join，或不阻塞父链的后台工作 | 固定 harness 支持两者；这些语料使用 spawn，不覆盖继承父上下文的 fork |
| 长 context、长输出尾部 | KV 容量、缓存恢复、偶发大 Prefill、长 Decode | 256k 版输入 P90=204,288、输出 P90=1,845 token；长度分布很宽 |

**不能把它细分成经过标注的“写代码／debug／搜索／规划”任务集。** 本次扫描的 256k 文件里，1,697 组 `subagent_type` 全部只是 `Subagent`；所有调用也缺少工具名／任务语义字段。标签不能支持 Explore、Plan 等任务比例统计。原始 `s/n` 是 streaming／normal API 类型，不是工作任务类别。

来源：[固定版 256k 数据说明](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126-256k/blob/8fecd2fc56694469f758f0afbbb6335ad3043740/README.md)、[官方方法页](https://inferencex.semianalysis.com/agentx/methodology)、[已下载的固定 harness FAQ](../../../datasets/agentx_20261030/harness/SemiAnalysisAI-agentx-harness-e4bb2f8/docs/benchmark-modes/semianalysis-agentx-faq.md)。

## 2. 完整数据与我们实际选取的负载

一“根会话族”包含主代理和所有子链；一“独立对话轨迹”只指其中一条链；一次“调用”是一次模型请求。下面的长度是请求加权均值，调用数是根会话等权均值。

| 指标 | 官方 full | 官方 256k | 当前固定八族 |
|---|---:|---:|---:|
| 根会话族 | 393 | 393 | 8 |
| 模型调用 | 98,827 | 68,266 | 171 |
| 每族调用：平均／中位数 | 251.5／86 | 173.7／70 | 21.4／21 |
| 有显式子代理的根会话族 | 175，44.53% | 175，44.53% | 2，25.00% |
| 显式子代理组 | 1,697 | 1,697 | 2 |
| 显式子代理调用占比 | 42.53% | 58.33% | 26.32% |
| 每调用输入：平均 token | 218,921.8 | 100,946.7 | 84,856.1 |
| 每调用输入：中位数 token | 142,016 | 88,768 | 63,168 |
| 每调用输出：平均 token | 1,077.4 | 860.3 | 435.7 |
| 每调用输出：中位数 token | 444 | 376 | 194 |
| 每族累计输出：平均 token | 270,927.5 | 149,437.2 | 9,313.5 |

full 的输入上限约 99 万；256k 版按每请求输入＋输出≤256,000 过滤，而不是把整段会话截成 256k。保留请求的相对时间不变。各输入长度是发布的哈希块口径，不应解读为原服务商精确计费 token。

我们的完整家族筛选条件是 4–80 调用、累计输出≤16,000、每请求输入＋输出≤256,000；34 族合格，导出 24 个候选，再固定其中 8 族。**因此当前样本天然偏短，不是 393 族的无偏样本。**

当前八族经固定 loader 重建为 **18 条独立轨迹＝8 条根链＋2 条显式子代理链＋8 条扁平辅助链**。171 调用分为根链 117、显式子代理 45、扁平辅助链 9。不能把额外 10 条链都叫真实多轮子代理。两条显式子代理在该重建图里均为后台分支；强前台子代理 fan-out／join 的覆盖不足。

原始模型字段也并非都相同：所选显式子代理 45 次均标为 Haiku，来源主流另含 Opus／Haiku 标签；**我们的实际回放全部运行 Qwen3.6-35B-A3B**，没有保留来源模型间的服务能力差异。字段计数仅表示 trace 标签，不验证这些模型名称的外部含义。

## 3. 当前怎么测

1. **输入与 DAG。** 固定官方 loader commit `e4bb2f835ffedbbe6b76252ea5c93caec68c5faf` 导出家族图；实际使用自写 replayer 调 SGLang `/generate`。以标记 token 和代码填充重建来源长度、块级前缀及依赖。输出温度 0、忽略 EOS，生成指定 token 数；下一轮输入按 trace 重建，不依赖实时生成文本。
2. **有限闭环回放。** C8 是八族一份；C128 是每族 16 份隔离副本，共 2,736 调用。C 表示客户端根会话数，不是单卡 Decode batch。依赖完成后发送后续请求；没有持续补充新家族的稳态计分窗口。只有全局无在途请求时，长空闲才压到 10 秒。
3. **模型与配置。** 两台各四张 H100 80GB，Qwen3.6-35B-A3B BF16；已有主混部点为 2×EP4、4×PP2、8×单卡；PD 点为 EP4 P→EP4 D、4P4D。EP4 的 Attention 为 TP1／DP4，MoE EP4；PP2 为分层 PP2／EP1。
4. **保留缓存。** 每 rank 开启 HiCache，CPU 32 decimal GB，GPU KV 使用原生容量。每轮前做非计时运行路径预热，正式轮开始前清空缓存；正式会话内不清缓存。每条独立对话固定其首次选择的实例／Attention-DP owner。
5. **统计范围。** 本报告缓存观察固定使用此前已审计的 21 个完整 episode、34,371 调用：18 个 E5/V3 混部，3 个 E7/V3 PD，每点三轮。新产生的 V4／新引擎数据不混入。V3 分支时序偏差及不同引擎、容量配置的限制继续保留。
6. **计时。** 请求 HTTP 开始→首输出为 TTFT，首→末输出除以输出间隔数为 TPOT，HTTP 开始→末输出为 E2E；请求就绪后的客户端等待另记。PD 真正交接 KV＋GDN；其 Prefill 工作量必须从 **P 端 `prefill_meta`** 读取。

当前所有主点均为固定分配，尚未用这些数据测出动态 EP／PP 配比的收益。合成内容也不能复现自然语言下的 MoE 专家路由分布。[完整协议及限制](../agentx_data_audit_20261031/REPORT.md)。

**最新修正时序的一轮补充另列：** 本次核查时，E8/V4 的 PP2 P＋EP4/EP2 D（2P6D）已有一轮 C8 完整 marker，171 调用；P 端总命中 91.4584%（全部 GPU，CPU 0%），平均新增 P 7,248.1 token。其输入／输出长度与所选来源逐请求相同。它不并入历史三轮均值；整个 pilot 仍在运行，不能视作四点整组验收。[独立数据与原始哈希](pilot_cache_supplement.json) · [pilot 进展入口](../agentx_2p6d_20261031/STATUS.md)。

## 4. “会话平均大小”分别是多少

| 单位／指标 | 平均 | 中位数 | P90 |
|---|---:|---:|---:|
| 每根会话族调用数 | 21.4 | 21 | 27.9 |
| 每独立轨迹调用数 | 9.5 | 2 | 24.6 |
| 每次调用完整输入 token | 84,856.1 | 63,168 | 175,872 |
| 每次调用输出 token | 435.7 | 194 | 789 |
| C8 实际新增 Prefill token／调用 | 7,245.1 | 1,664 | 14,080 |

每族平均累计输入 **1,813,800 token**、累计输出 **9,313.5 token**；每独立轨迹分别为 806,133.3 与 4,139.3。累计输入会在每轮重复计算前缀，**不是需要常驻的 KV 大小**。18 条轨迹有 8 条只有一次调用，所以“平均每会话 9.5 轮”和“中位数 2 轮”同时成立。

另外，“先对每条轨迹求平均，再把 18 条轨迹等权平均”的输入是 45,603.5、输出是 610.0 token；它与上表请求等权均值回答的是不同问题。后续报告应优先固定单位，避免混用。

## 5. 缓存与所谓“prefetching 命中率”

这里已有的是 **prefix caching／前缀复用** 数据。主表命中率按 token 加权：Σ命中输入 token／Σ完整输入 token；GPU、CPU 列的分母也都是完整输入。CPU 命中避免重算，但仍可能有状态／数据恢复成本。

| 8 GPU 部署／历史 cohort | C | 总前缀命中 | GPU 命中 | CPU HiCache 命中 | 平均新增 P token |
|---|---:|---:|---:|---:|---:|
| 2×EP4，E5/V3 | 8 | 91.46% | 91.46% | 0.00% | 7,245.1 |
| 4×PP2，E5/V3 | 8 | 91.46% | 91.46% | 0.00% | 7,245.1 |
| 8×单卡，E5/V3 | 8 | 91.46% | 91.46% | 0.00% | 7,245.1 |
| 2×EP4，E5/V3 | 128 | 84.05% | 79.08% | 4.97% | 13,537.9 |
| 4×PP2，E5/V3 | 128 | 88.62% | 86.75% | 1.87% | 9,659.0 |
| 8×单卡，E5/V3 | 128 | 52.68% | 9.32% | 43.36% | 40,157.6 |
| EP4 P→EP4 D，E7/V3；P 端 | 128 | 43.30% | 42.14% | 1.16% | 48,116.0 |

这是各部署的实际缓存观察，包含容量、回放时序、粘性分配及状态管理影响；**不能把差值单独归因于 EP／PP 内核，亦不能把 E7 PD 与 E5 混部当作同源 PD 因果对照。**

### 为什么更换布局会改变命中率

上表的 **2×EP4、4×PP2、8×单卡全部是 P/D 混部**：同一请求的 P、D 在同一实例执行，PP2 的两个 stage 共同承担这两阶段。只有单独标明 P→D 的行属于跨实例 P/D 分离。

输入中的块级前缀关系没有因布局改变；变化的是运行时保留并恢复这些前缀的能力。实际启动分配如下，token 容量按完整模型归一化，PP 两个 stage 的同一 token 只计一次：

| 8 GPU 布局 | 独立缓存池 | 每池 GPU KV 容量约 token | 合计有效容量 token | 每池 C128 根会话数 |
|---|---:|---:|---:|---:|
| 8×单卡 | 8 | 339,000 | 2,712,832 | 16 |
| 4×PP2 | 4 | 3,771,000 | 15,083,904 | 32 |
| 2×EP4；Attention-DP4 | 8 | 2,226,000 | 17,806,080 | 16 |

单卡副本在每张 GPU 上放完整权重，剩余 KV 空间明显小；这与 C128 时 GPU 命中仅 9.32%、CPU 命中 43.36% 的观测相符。它支持“GPU 缓存压力很大”的判断，尚未隔离出每一次 miss 的具体原因。C8 的所有混部缓存统计相同，则说明本次低负载下三者得到相同的实际复用前缀；91.46% 已包含首次访问及前缀变化，不应期待必然达到 100%。

**PP2 与 EP4 的差别不能仅按总容量解释。** EP4 总 KV 更多，但分成八个 Attention-DP 池；PP2 是四个更大的分层池。各独立池不会自动共享空闲 KV 资源。根会话数和根输入量已经均衡，子链首次到达次序、局部压力及执行进度仍会不同。已存三轮中，跨位置新增 P 工作量的 CV，EP4 平均 0.642、PP2 平均 0.040；这描述局部差异，不证明是哪一项导致。

此模型还要求 **对应前缀边界的 GDN／recurrent state 可用**。有 Attention KV 块不保证可以从同一边界恢复。实际单卡每池 40 个 GPU GDN 槽，EP4 每 Attention-DP 池 80 个，PP2 每 stage 160 个；PP stage 只保存自身层，不能把槽数直接当作状态内存倍数。HiCache 的有限 host 池也不保证所有已访问状态永远保留。

“请求被发到别处”也不足以解释主要差距：已有同 owner 历史 hash 前缀机会平均约 77,800 token／调用，放宽到任意 owner 只增加约 44–51 token；而实际 C128 缓存均值为 EP4 71,318、PP2 75,197、单卡 44,699。该离线机会未模拟 KV／GDN 的真实可用性，所以不能把差额全部称为驱逐；但证据不支持把数千至数万 token 的差距主要归于跨 owner 前缀共享。

可以确定缓存容量、分池和运行历史都变了；容量驱逐、GDN 状态、写回／恢复、调度各贡献多少，仍需受控拆分。本组适合比较固定 GPU 预算下的完整部署效果，不能作为“同等缓存条件下，纯 EP／PP 计算差异”的测量。

**主动 prefetch 尚无可报告的命中率。** 现有字段没有“预测了哪些块／何时开始搬／请求使用时是否已完成／搬了但未使用多少”的完整事件记录。HiCache 命中不等于预取预测正确，也不等于搬运被隐藏。若要研究预取，应分别记录使用量／预取量、需求覆盖、及时完成率和暴露恢复时间，而不是给现有 prefix 指标换名。

## 6. 进一步探索得到的负载特征

| 观察 | 绝对数据与口径 | 对实验的含义 |
|---|---|---|
| 大 context 只占部分调用 | 输入≥131,072 的 37/171 调用，占 21.64%；贡献 45.11% 的累计输入 token | 按请求数均衡不保证缓存工作集均衡 |
| 少数长输出贡献大量 Decode | 输出≥2,048 的 6/171 调用，占 3.51%；贡献 33.47% 的输出 token | 平均 TPOT 应同时报告按 token 间隔加权的结果，不能只给短／长请求同权均值 |
| 大部分调用输出较短 | 输出<512 的 134/171 调用，占 78.36% | 当前负载对长 Decode 稳态的覆盖有限 |
| 共享前缀潜力高 | 独立轨迹中 153 对相邻调用，后请求输入中 93.57% 与前输入共享连续前缀；8 对出现 context 缩短 | 支持研究缓存亲和；长度缩短或前缀失配本身不能证明发生了语义 compaction |
| 冷／失配尾部主导新增 Prefill | C8 约 13.45% 请求完全未命中，却贡献 65.38% 新增 P；新增 P 最大的约 10% 请求贡献 73.46% 新增 P | 只看平均输入或中位新增 P，会低估少数大 Prefill 的调度干扰；“未命中”不全是首次调用 |
| 首轮与后续不同 | C8 每独立轨迹首调用平均输入 16,327.1、命中 0%；后续平均输入 92,918.4、新增 P 6,176.6、token 加权命中 93.35% | 不应以每个请求都冷启动的 synthetic P 曲线代表全部 AgentX |
| P／D token 比随部署改变 | 完整输入／输出比固定 194.75:1；C8 新增 P／D=16.63:1；C128 的 EP4／PP2／单卡为 31.07／22.17／92.16:1 | workload 不是与部署完全独立的一个“Prefill 比例”；这些仍是 token 比，不是 GPU 时间比 |
| C 不能当作本地 Decode batch | 既有 forward 计数：C128 的 EP4／PP2／单卡本地纯 Decode batch 均值约 5.62／5.04／2.21 | 与 synthetic B64／B128 不同；EP 为 Attention-DP 本地，PP 仅 stage0 的一次 forward |

最后一行来自 [原 forward 计数报告](../../agentx_pd_dynamic_20261030/matrix_analysis/FORWARD_BATCHES.md)：各轮先按 forward 次数加权 batch，再对三轮求均值；不含 EXTEND／MIXED，不是时间加权并发，也不是整个 EP 组的 token 数。

原始时间特征也有明显长尾：256k 的 `think_time` 中位数 1.172 秒、P90 10.455 秒，但平均 174.159 秒；这些是来源元数据，不能等同真实工具执行耗时或 H100 的服务时间。子代理组来源持续时间平均 377.4 秒、中位数 136.0 秒；所选两组平均只有 90.3 秒。当前八族的源时间跨度中位数 366.5 秒，但一族达到约 40.3 小时，因而压缩后整轮墙钟不能解释为原始生产流量的请求到达率。

## 7. 现有数据适合回答什么，缺什么

现有样本最适合观察 **长前缀多轮请求，在不同容量与分配下产生的缓存／新增 Prefill 差异，以及大 Prefill 对短 Decode 的干扰**。它对长会话生命周期、长输出占主导、多个前台子代理同时运行并 join 的覆盖不足。不能仅凭这八族推断全部 AgentX 的 P/D 或动态布局收益。

补 workload 时，优先按现有语料挑三组完整家族：高前缀复用且短输出、较长输出、较强前台多分支。保留同一固定引擎／回放版本和 HiCache；每组同时记录真实本地 batch、P 端新增输入、GPU／CPU 缓存、ready 延迟与输出 token 加权 TPOT。这样比先扩大 C128 的副本数更能检查当前结论的适用范围。本报告未启动这些补实验。
