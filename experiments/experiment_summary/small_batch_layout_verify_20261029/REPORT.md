# 35B 小 batch：四张 H100 的整模型验证

问题：固定 GPU 缓存、相同输入和四卡预算，在全组 N=8、16、32 的 Decode 中，PP 是否反超 EP4？两个 H100 节点并行实验，每个节点都有自己的 EP4 对照。

所有数值都是 5 轮算术平均。TPOT 先逐请求计算 `(最后 token − 首 token)/127`，再对请求和轮次求平均；请求 E2E 包括 TTFT。没有选择最大值或最快样本。

## 判断

- 平均 TPOT：N8：PP2 延迟低 10.2%；N16：PP2 延迟低 0.7%；N32：EP4 延迟低 9.8%。
- 平均请求 E2E：N8：PP2 延迟低 17.9%；N16：PP2 延迟低 9.3%；N32：EP4 延迟低 1.7%。

优化 PP2 与 EP4 在同一 Decode 阶段内出现了可重复的 TPOT 换边，双向幅度约 10%。但含 TTFT 的整请求结果中，较大 N 的 EP4 收益很小；当前数据不足以支持“动态切换能获得双向很大的整请求收益”。小 N 时，四个单卡副本相对同节点 EP4 的收益更大，也必须进入候选集。尚未测量实例分流、状态迁移或布局切换开销。

## 固定条件与边界

- 完整 Qwen3.6-35B-A3B BF16，40 层、256 个 routed experts、top-8。每条请求通过真实 Prefill 建立 P=4096 token 的 GPU KV/GDN 缓存，Q=1，O=128，忽略 EOS；每个请求严格检查 device cached_tokens=4096、完整输出 128。没有 CPU HiCache/KV 恢复。
- 输入为固定 repeated 模板及每请求独立标记，贪心生成；不是在线生产流量或任务质量评估。
- EP4 是 Attention DP4/TP1、MoE EP4、PP1；2×PP2 是两个独立实例，每实例两阶段、两微批；4×单卡是四个完整模型副本；PP4 为四阶段原生调度。
- EP4 每 rank 的请求数为 N/4；2×PP2 每实例 N/2、每微批 N/4；固定请求分组与 EP4 对齐，等待合批保留在延迟里。新增 B2 通信形状保留原生预热 schema 检查；每个 PP2 点逐请求核对原生固定分组与 lookahead 的输出，并检查四个 stage 的 lookahead 执行及退休计数。
- 所有布局使用同一小 token Expert Triton 内核家族、原生 Attention/GDN；完整模型和真实权重资格检查通过。实际 rank/stage batch 与 Graph 资格计数见各运行 forward_histograms.csv。
- 两个节点各自顺序测候选布局；跨节点 EP4 不求平均，也不把跨节点数值当作因果对照。尚未做布局交替复测、其他上下文或其他模型；PP4 未应用仅支持 PP2 的 lookahead。
- 这里是同一 Decode workload 类别内的结果。Q1 的 TTFT 不能代替冷 Prefill 性能；自然生成的路由随 batch/数值变化，不能把差异全部拆成通信和 Expert 的因果贡献。

## 如何理解旧组件预测

旧图的小 N 正预算，只表示省下的专家通信能否支付额外 Expert 计算；它假设流水充分填充，未计入阶段交接、反馈、调度等待和 Attention/GDN。旧图中相同的 EP/PP Expert 数值来自相同的合成微批 lookup，也没有独立测量 EP 每 rank 64 个常驻专家与 PP 单层 256 个常驻专家的实际执行。因此它是候选区域，不能视为 PP 整模型胜出的预测。
