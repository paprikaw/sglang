2026-11-05。后续按这份约定开发，GitHub 上的分支和 PR 是查看实现进度的入口。

**共同基线。** `codex/pp-elastic-integration` 是已经整理并做过有限范围回归的共同分支，冻结标签为 `baseline/sglang/ep-pp-pd-20261105`。原来的 `codex/autoscaling-kvcached` 和实验 worktree 保留历史，不作为新任务默认合并目标；上游 `sgl-project/sglang` 也不是本项目的提交目标。

**一期总 PR 已合并。** `codex/pp-hicache-autoscaling` 的 [总 PR #1](https://github.com/paprikaw/sglang/pull/1) 已于2026-11-09合入共同基线，Runtime #2 和 Cache #3 均已合并。当前是有界验收的 naive PP＋HiCache 基线，具体范围与冻结标签见[验收摘要](BASELINE_ACCEPTANCE_20261109.md)。下一阶段仍由主 agent 维护项目分支；有首个交付后建立新的总 PR，子任务 PR 指向项目分支，最后再合共同基线。低干扰机制和动态 P/D 接入尚未完成。

**二期集成。** [任务PR #4](https://github.com/paprikaw/sglang/pull/4)于2026-11-11以`69dc304d8072`合入项目，项目整棵树与通过992项CPU检查的`4d7638b01ac2`一致。当前native／HiCache／NIXL在线KV迁移与启动预捕获已有有限A100验证；[总PR #5](https://github.com/paprikaw/sglang/pull/5)负责合回`codex/pp-elastic-integration`，其GitHub合并记录是共同基线状态的依据。本轮直接实施和审查，没有新增独立reviewer；全仓CI欠账及未测组合见[审查记录](REVIEW_20261111.md)。下一阶段仍从共同集成分支派生任务分支，不回到旧的脏autoscaling工作区。

**子任务。** 需要并行时，每位 agent 从明确的项目提交建立独立的 `codex/` 任务分支和 worktree，并向项目分支开一个 Draft PR。按可独立检查的任务划分 PR，而不是每个 commit 都开 PR。依赖其他子任务时写清依赖链接和起始 SHA；优先等依赖合入项目分支后再开展，确需堆叠时明确标注。主 agent 在总 PR 里用列表维护任务、负责人、子 PR、依赖、已合入状态和测试结果。

**提交频率。** 完成一个可检查的修改点、开始长实验前、交接或结束工作前，均提交并推送。持续实现时尽量每 30–60 分钟形成一次有意义的检查点；未完成内容如实标注，PR 保持 Draft。一次 PR 可以持续增加提交。只提交本任务文件，不把历史脏工作区、其他人的修改、权重、密钥和大量结果一并加入。

**评审与合并。** 主 agent 检查子 PR 的代码、相关测试和依赖，逐个合入项目分支并处理冲突；共享分支使用 merge commit 保留祖先关系，避免强推改写已经评审或正在被依赖的提交。子 PR 通过只说明各自变化通过检查，总 PR 还必须验证组合后的提交。总 PR 准备完成后，统一合入 `codex/pp-elastic-integration`；保留有历史用途或未提交内容的 worktree。

**验证与实验。** PR 说明具体改动、实际运行的检查、失败及未验证项，不把旧基线的 537 项 CPU 回归和静态 A100 检查当作新机制已通过。实验使用已推送的 SHA、不可移动标签和依赖／运行适配记录；开始 GPU 实验前走 Experiment Guard。原始大结果在实验目录保存，PR 链接到精简报告及可核验记录。

**如何查看。** 日常看总 PR 的任务列表和最新提交；需要审查一个实现时进入对应子 PR；需要复现实验时使用报告中的准确 SHA 与标签。完成状态以 GitHub 实际推送和测试记录为准。

**分工与阶段。** naive 基线保留 Runtime（PR #2）及 Cache（PR #3）的交付与独立审查记录。2026-11-09 用户要求本轮不使用子 agent，Memory、Graph／Runtime、Patch 只作为模块边界，由主 agent 顺序实现和自行检查。首项按层映射已进入实现；未经独立审查或硬件验收的内容保持 Draft，不据此宣布完成验收。无论怎样分工，同一时段仅有一名 GPU 运行、监控、清理和归档负责人；主协调器负责决策、关键证据验收及顺序合并。

**任务交付与清单。** 每个 agent 交付前负责更新自己的条目，附版本、必要证据和未解决问题；代码完成、CPU 通过与 GPU 验收分别记录。子分支上的清单更新随 PR 合入；若未含清单或主协调器正独占写入，则提交明确的条目补丁，由主协调器顺序落盘。失败或阻塞也要记录，未满足条目验收条件不勾选。新增任务先登记，避免靠聊天追踪；不覆盖其他条目，不复制详细日志。

**协调与证据复用。** 相同内容哈希、配置和检查项的通过证据直接复用，变更相关路径或发现矛盾后才重测。每个冻结交付做一轮独立审查，由 Runtime 统一归档；仅在新阻塞、接口变化、具体审查发现或冻结交付时发送协调消息。有界任务交付后返回，不为待命循环查询。当前命令、实验、Guard 心跳和清理时限不因协调节流而改变。
