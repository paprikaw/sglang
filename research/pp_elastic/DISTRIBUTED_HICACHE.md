# PP 切换时，历史 CPU 缓存能否晚一点搬？

2026-11-13。代码核对基于 `05d823897a`。这是候选设计，尚未实现或做新 GPU 实验；进度见[统一清单](TODO.md)。

**结论。** 可以把活跃请求接班和历史前缀搬运分开：权重、活跃 KV、最新 GDN 和请求进度准备正确后先切换，历史 CPU 前缀继续留在旧池，按需读取并在后台整理。历史缓存未全部迁完，不应天然成为恢复推理的条件。

**当前怎样做。** 现在不是把整个 CPU HiCache 恢复到新 GPU，而是按新的全局层归属，把有效 CPU 缓存行复制到新布局的 CPU 池。已有后台快照／预搬，但最终仍排空 HiCache I/O，核验当前内容、同步变化并挂接完整目标池；发布后退休旧池。新请求随后从自己的 CPU 池恢复前缀，没有向旧池按需取数的路径。见 `hicache_transition.py` 的 `snapshot_at_fence`、`commit`、`release_retired`，及[当前实现](HICACHE_BACKGROUND.md)。

**为什么值得考虑。** 最新有界缩容实验最后暂停约87 ms，其中源rank的 CPU 快照／内容核验约39.8 ms；后台虽然提前搬完稳定 CPU 数据，仍要检查整个受影响历史集合。缓存变大时，这种依赖可能更重，但目前只有小规模单轮证据，不能直接预测改后暂停或按容量线性外推。

**已有后端能用多少。** SGLang 的 L2 是实例私有 CPU 内存，跨实例共享走配置好的 L3。NIXL 支持 DRAM／VRAM 传输，但本仓库的 `storage/nixl` connector 主要连接 CPU 池与文件／对象存储，并不自动提供旧 worker CPU 池的远程查找。当前弹性 PP 还在 `assert_host_quiescent` 中明确拒绝 `enable_storage`。因此不能仅加 `--hicache-storage-backend nixl` 就完成本方案，仍需处理动态层归属和旧缓存生命周期。[SGLang 官方设计](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/hicache_design.mdx)，[NIXL API](https://github.com/ai-dynamo/nixl/blob/main/src/api/python/_api.py)。

**最小接入范围。** 先沿用同节点 PP2↔PP3、HiCache、已有 GPU→GPU KV patch 和候选权重 offload。建立独立于 PP rank 的缓存目录，以模型／格式身份、前缀块、全局层号及状态类型定位旧 CPU 数据。切换时发布必要的目录引用，不扫描搬运全部历史载荷。新请求先查本地，再查旧池，只等自己缺少的前缀和配套 GDN 状态；验证失败或读取失败的历史前缀按未命中处理并重算，不能拼接不完整的 hybrid 状态。

**源池怎样保留。** 被读取的缓存块必须有租约或引用计数，防止旧池逐出、覆盖或复用；地址不能替代块的版本。已发布历史块保持不可变，发生写入时另分配版本。目标确认接收后才更新该块位置，读者结束后才释放旧副本。新写入归新布局，避免两个布局同时改同一份状态。第一步可以保留旧 CPU 池，但真正允许旧 GPU worker 退出，需要 CPU 服务或共享内存持有者独立管理其生命周期；留下裸指针不够。

**同节点先简化。** 当前往返实验的多个 worker 在同一物理节点，旧池和新池都位于该主机 RAM。优先评估共享 CPU 缓存及受控视图，避免无意义的 CPU→CPU 重复制；这仍需修改当前本地池与层映射接口。跨节点再用启动时准备好的 NIXL 通道读取远端 DRAM，实际是否 RDMA 要按链路验证。NIXL 负责搬数据，目录、缓存一致性和回收仍由我们实现。

**后台做什么。** 优先整理热前缀，限速搬运，避免争抢推理所需的 PCIe／内存带宽。冷块可以留在旧 CPU 服务直到逐出，不要求最终无条件复制全量；若需要归还源主机，则必须在退出前迁移或逐出余下块。总 CPU 预算包含旧池、新池和临时副本。

**仍须同步什么。** 当前活跃请求的最后 KV patch、最新 GDN、请求进度和提交共识不能因历史缓存远程可读而省略。方案把一部分工作从切换时转到新请求首次命中时，可能增加该请求的 TTFT；不是消除传输成本，也不能承诺约87 ms再直接减去39.8 ms。

**怎样验证。** 用相同输入、缓存和权重条件，对照现在的完整 CPU 交接与按需读取，先做一次短往返：切换后主动请求仍只在旧池的前缀。记录最后暂停、准备期 token 间隔、远程命中／读取字节、首次与重复请求 TTFT、输出一致性和 CPU 峰值；故障检查旧块回收、槽位复用及源服务退出。之后再增加历史缓存容量，检查开销是否仍随历史集合增长。上述实验尚未启动。
